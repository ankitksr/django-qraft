django-qraft — how a task actually flows

One spine: enqueue → broker → worker → monitor → hook. Everything else (retry, crash recovery, workflows, django.tasks, throttling) hangs off that spine. Every box carries the module that owns it.

1 · The process tree (worker lifecycle)
Qraft subclasses two django-q2 pieces and overrides three methods. Everything else is inherited.
2 · The spine — one task, happy path
Read it as a snake: left→right, then right→left, then left→right.

ChainDispatcher

qraft/dispatchers.py
  • Locks the chain, compares current_step_index — a duplicate delivery bails here.
  • Next step needs approval ⇒ park in WAITING_APPROVAL.
  • No next step ⇒ complete chain + chain-level hook.
  • Step failed and task is EXHAUSTED ⇒ chain FAILED. Mid-retry ⇒ do nothing.

ParallelDispatcher (iter / batch)

qraft/dispatchers.py
  • Only counts terminal attempts (succeeded, or task EXHAUSTED).
  • Increment under select_for_update(); attempt.counted flag makes it idempotent.
  • completed == total ⇒ workflow hook, once, via WorkflowHookDispatch.
  • Not yet complete ⇒ optional progress_hook fires each time.
3 · Failure lane — the retry round trip
A retry leaves Qraft entirely and comes back through a django-q2 Schedule row. That round trip is what Phase 2 deletes.
4 · Crash lane — the reaper
django-q2 writes its Task row only at completion, so "no result row" alone proves nothing. The lease supplies the liveness signal.
5 · Side entrances onto the spine
Four other ways work gets in. All of them land back on step 3 (or step 8) of the spine.

Workflows

qraft/chain.py · iter.py · batch.py
  • Chain.run() → chain model + steps, then queues one step; the dispatcher queues the next.
  • Iter.run() / Batch.run() → fan out every task at once, total_count set up front.
  • All go through _create_workflow_task(), which reuses the same one-transaction enqueue.
  • Workflow tasks never carry task-level hooks — workflow-level only.

django.tasks backend (Django 6)

qraft/backend.py · qraft/runner.py
  • .enqueue() → qraft.tasks.async_task queuing run_task, which unwraps the @task decorator wrapper at execution time.
  • run_after → Schedule + marker, exactly like a retry; attempt 1 is created only when it fires.
  • takes_context=True bypasses async_task: it builds the QraftTask + attempt itself and queues run_task_with_context.
  • get_result() reads QraftTask + its attempts.

Throttle

qraft/throttle.py
  • @throttled(key, rate) withdraws tokens from a shared RateBucket row under select_for_update().
  • Denial raises RateLimited — a member of RATE_LIMIT_EXCEPTIONS, so lane 3 takes the rate-limit branch.
  • SQLite has no real row lock: correct, but not concurrency-safe there.

Priority lanes

qraft/brokers.py
  • Three lanes on one OrmQ table: {key}--high, {key}, {key}--low; first non-empty wins each dequeue.
  • Enqueue side always writes the lane; only a cluster running QraftOrmBroker drains high/low.
  • Known gap: a scheduled retry re-enters the default lane.

7 · The bits that surprise you six months later
  • Retry is checked before workflow routing. A failing chain/iter/batch task that still has retries schedules one and returns — the dispatcher never sees it that round.
  • skip_exceptions beats the rate-limit set. "Rate limits are always retryable" is only true relative to a restrictive retry_exceptions allowlist.
  • A scheduled retry sets QraftTask → PENDING, not FAILED. FAILED only survives when there is no policy at all.
  • The marker is not the Schedule's name. Schedule.name is qraft_retry:{id}:{n}; the marker qraft:{id}:{n} travels in kwargs as q_options.task_name and becomes the q2 Task name.
  • Two cadences, not one. The sentinel guard loop runs every 0.5s (GUARD_CYCLE); the Q2 scheduler is what runs every ~30s.
  • Heartbeat staleness has a floor. The reaper uses max(3 × heartbeat_interval, 90s), and also requires the task RUNNING and the attempt unresolved.
  • Non-ORM broker only disables half the reaper. Stale-heartbeat orphans are still reaped; only the never-started branch needs the OrmQ lookup.
  • dead_letters() includes FAILED. A failure with no retry policy lands in the DLQ without ever being EXHAUSTED.
  • post_execute cannot close the lease. It fires in the monitor, not the worker — the threaded worker calls stop_heartbeat() itself; other paths rely on the loop's own zero-row UPDATE or the deadline backstop.
