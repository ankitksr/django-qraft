django-qraft — lifecycle map

One spine: enqueue → queue → worker → monitor → hook handler. Everything else — retries, crash recovery, workflows, hooks — branches off the hook handler. Postgres rows are the source of truth at every step.

3 · Side entrances onto the spine

Workflows chain.py · iter.py · batch.py

  • QraftChain: one step queued at a time; a gated step parks the chain in WAITING_APPROVAL until approve() / reject().
  • QraftIter / QraftBatch: fan out all tasks; locked counters + a counted flag; the workflow hook fires exactly once.
  • Workflow tasks carry workflow-level hooks only.

django.tasks backend backend.py (Django ≥ 6)

  • @task.enqueue() → the spine, via qraft.runner.run_task (unwraps the decorator's non-callable wrapper).
  • run_after → Schedule row + marker, like a retry.
  • takes_context=True → run_task_with_context builds the TaskContext worker-side.
  • get_result() reads QraftTask; statuses map to READY / RUNNING / SUCCESSFUL / FAILED.

Throttle throttle.py

  • @throttled(key, rate, capacity) draws tokens from one shared RateBucket row under a row lock.
  • Empty bucket → RateLimited → the rate-limit retry class reschedules with backoff.

Priority lanes brokers.py

  • QraftOrmBroker drains --high, then default, then --low on one ORM queue.
  • Requires Q_CLUSTER["broker_class"]; on any other broker high/low tasks strand — never pass a priority on Redis.
  • Scheduled retries re-enter on the default lane (phase 2 fixes this).

4 · The bits that surprise you six months later

  1. The retry check runs before workflow routing; a retrying chain/iter step does not advance or count its workflow that round.
  2. skip_exceptions beats the rate-limit class; the rate-limit set only overrides a restrictive retry_exceptions allowlist.
  3. A scheduled retry flips the task back to PENDING; the marker rides in Schedule.kwargs → q_options.task_name, not in Schedule.name.
  4. Two cadences: the sentinel guard loop runs every 0.5s; the Q2 scheduler (which fires retries) every ~30s.
  5. Heartbeat staleness = max(3 × heartbeat_interval, 90s), and reaping also requires task RUNNING + attempt unresolved.
  6. On a non-ORM broker the reaper skips only never-started attempts; stale-heartbeat orphans are still reaped.
  7. A reaped task with no retry policy goes to FAILED, not EXHAUSTED — both land in dead_letters().
  8. ParallelDispatcher also fires progress_hook on every non-final completion.
  9. async_task rejects sync=True, save=False, cached — attempt resolution needs a saved result after the attempt row exists.
  10. The threaded worker stops its own heartbeat; post_execute fires in the monitor, so it cannot do that job alone.
  11. Requeued takes_context tasks do not get TaskContext re-injected (documented gap).
  12. Idempotency keys block re-enqueue permanently by default; idempotency_retry_dead=True reclaims a FAILED/EXHAUSTED key.
